# Especificación comparativa: IEEE 29148 vs. Historias BDD

**Historia de origen:** HU-01 — Registro de Agricultores
**Priorización:** Must have · **Estimación:** 3 puntos

---

## 1. Historia de usuario original (referencia ágil + BDD)

> **Como** Agricultor, **quiero** registrarme en la plataforma **para** ofrecer mis productos.

**Escenario BDD**

- **Given** el usuario cuenta con información personal válida y desea registrarse como agricultor.
- **When** completa el formulario con su nombre, número de identificación, municipio, teléfono, correo y contraseña, y selecciona la opción "Registrarse".
- **Then** el sistema guarda la información del agricultor y muestra un mensaje confirmando que el registro se realizó correctamente.

---

## 2. Reescritura formal según IEEE 29148

### 2.1 Requisito de las partes interesadas (StRS)

| Campo | Contenido |
|---|---|
| **ID** | StRS-001 |
| **Parte interesada** | Agricultor |
| **Enunciado** | El agricultor requiere poder registrarse en la plataforma para ofrecer sus productos en ella. |
| **Justificación** | Sin un registro previo, la plataforma no puede identificar a los oferentes ni asociarles productos. |
| **Prioridad** | Alta (Must have) |

### 2.2 Requisitos del sistema (SyRS)

| ID | Enunciado normativo | Prioridad | Verificación |
|---|---|---|---|
| **SyRS-REG-001** | El sistema deberá proporcionar un formulario de registro de agricultores. | Alta | Inspección / Prueba |
| **SyRS-REG-002** | El sistema deberá solicitar en el formulario, como mínimo, los siguientes datos: nombre, número de identificación, municipio y datos de contacto. | Alta | Inspección / Prueba |
| **SyRS-REG-003** | El sistema deberá validar que todos los campos obligatorios estén diligenciados y que su formato sea válido antes de aceptar el registro. | Alta | Prueba |
| **SyRS-REG-004** | El sistema deberá almacenar de forma persistente la información del agricultor cuando el registro sea aceptado. | Alta | Prueba |
| **SyRS-REG-005** | El sistema deberá mostrar un mensaje de confirmación al agricultor cuando el registro se complete correctamente. | Alta | Prueba |
| **SyRS-REG-006** | El sistema deberá informar al usuario, indicando el campo afectado, cuando los datos sean inválidos o incompletos, sin almacenar el registro. | Media | Prueba |
| **SyRS-REG-007** | El sistema no deberá permitir dos registros de agricultor con el mismo número de identificación. | Media | Prueba |

### 2.3 Atributos de cada requisito

| Atributo | Valor |
|---|---|
| **Fuente** | HU-01 (Product Owner) |
| **Estado** | Propuesto |
| **Riesgo** | Bajo |
| **Dependencias** | Ninguna (requisito base para publicación de productos) |
| **Método de verificación** | Prueba (ver matriz de trazabilidad) |

### 2.4 Supuestos y puntos por definir

Las siguientes decisiones no están en la historia original y deben confirmarse con el Product Owner. Se agregan aquí para que los requisitos sean **inequívocos y verificables**, como exige la norma:

1. **"Información personal válida":** no se especifican reglas. Se asume que el número de identificación debe ser numérico y no vacío, y que los datos de contacto incluyen al menos un teléfono o un correo electrónico con formato válido.
2. **Municipio:** se asume selección desde una lista de municipios y no texto libre.
3. **Duplicados:** se asume que el número de identificación es único por agricultor (SyRS-REG-007).
4. **Tratamiento de datos personales:** el almacenamiento de datos personales debe cumplir la normativa aplicable de protección de datos (en Colombia, Ley 1581 de 2012). Esto puede derivar en un requisito no funcional de autorización del titular.

## 3. Matriz de trazabilidad

| Requisito | Origen | Elemento del escenario BDD | Caso de prueba |
|---|---|---|---|
| SyRS-REG-001 | StRS-001 | When (formulario) | CP-01: el formulario de registro se muestra |
| SyRS-REG-002 | StRS-001 | When (nombre, apellido, identificación, municipio, telefono, correo, contraseña) | CP-02: el formulario contiene los cuatro campos |
| SyRS-REG-003 | StRS-001 | Given (información válida) | CP-03: se rechaza el registro con campos vacíos o con formato inválido |
| SyRS-REG-004 | StRS-001 | Then (guarda la información) | CP-04: el agricultor queda persistido tras registrarse |
| SyRS-REG-005 | StRS-001 | Then (mensaje de confirmación) | CP-05: se muestra el mensaje de éxito |
| SyRS-REG-006 | StRS-001 | (no cubierto por el escenario BDD) | CP-06: se muestra el error del campo afectado y no se guarda |
| SyRS-REG-007 | StRS-001 | (no cubierto por el escenario BDD) | CP-07: se rechaza una identificación ya registrada |

> Observación: SyRS-REG-006 y SyRS-REG-007 aparecen al formalizar y no estaban cubiertos por el escenario BDD original (que sólo describe el camino feliz).

## 4. Matriz comparativa

| Criterio de ingeniería | Especificación formal IEEE 29148 (SyRS) | Historia de usuario ágil + BDD |
|---|---|---|
| **Propósito y enfoque** | Documentación prescriptiva, exhaustiva e inmutable para acuerdos contractuales. | Carta de conversación ágil, ejecutable y enfocada en el valor continuo del usuario. |
| **Sintaxis y estructura** | Cláusulas normativas estructuradas ("El sistema deberá proporcionar…"). | Formato "Como [Rol] quiero [Acción] para [Beneficio]" + escenarios Given-When-Then. |
| **Validación y pruebas** | Matriz de trazabilidad de requisitos y casos de prueba manuales. | Especificación ejecutable traducible directamente a métodos `@Test` en JUnit 5. |
| **Gestión del cambio** | Requiere comités formales de control de cambios (CCB) y revisiones rígidas. | Refinamiento continuo (Backlog Grooming) adaptativo al inicio de cada Sprint, por el Product Owner. |

### 4.1 Lo observado al aplicar ambos enfoques a HU-01

- **Granularidad:** la historia produjo 1 enunciado y 1 escenario; la forma IEEE produjo 7 requisitos individualmente verificables.
- **Casos límite:** el formato formal obliga a explicitar validaciones, errores y unicidad, que el escenario BDD no cubre.
- **Ejecutabilidad:** el escenario Given-When-Then se convierte directamente en un `@Test` de JUnit 5; los requisitos IEEE necesitan un paso adicional de derivación de casos de prueba.
- **Costo de cambio:** modificar una regla (por ejemplo, un nuevo campo obligatorio) en el formato formal implica actualizar requisitos, trazabilidad y pasar por control de cambios; en BDD basta con ajustar el escenario en el refinamiento del Sprint.
- **Uso recomendado:** el enfoque formal es más adecuado cuando hay acuerdos contractuales o necesidad de auditoría; BDD, cuando se busca entregar valor iterativo y mantener pruebas vivas.
